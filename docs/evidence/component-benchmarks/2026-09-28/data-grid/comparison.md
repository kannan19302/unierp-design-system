# DataGrid / SpreadsheetGrid comparison — 2026-09-28

## Scope and identity

The package exports `SpreadsheetGrid` and aliases it as `DataGrid`. It is an uncontrolled client-side cell editor with a spreadsheet formula-bar appearance, row/column coordinate headers, arrow-key selection, and `onChange` emitting a two-dimensional string/number matrix. The Storybook `BudgetForecasting` example presents a financial worksheet. This is a different job from the shared `DataTable` or native `Table`: spreadsheet-like cell editing, not querying and managing a record collection.

The local `compositions-spreadsheetgrid--budget-forecasting` story was visually and AX-inspected at 1280×720. It displays 6 rows × 7 columns of quarterly plan values with a row-number gutter, active A1 cell, coordinate pill and input labelled “Formula Bar Input.” A read-only browser interaction moved selection to D3 with an arrow key, Enter entered the D3 edit input, and Escape exited; Escape returned focus to the web area rather than visibly restoring focus to the grid. This was manual Storybook inspection, not an automated test. Same-session captures were inspected but not retained.

## References and benchmark decision

No first-party shadcn spreadsheet editor was found. The official [shadcn Data Table guide](https://ui.shadcn.com/docs/components/base/data-table) explicitly treats its example as a composable TanStack record table: select the feature set (filtering, pagination, sorting, selection, visibility), then compose around the consumer’s columns and data. This is useful for distinguishing Strata’s grid job from an ordinary table; it is not an editing equivalent. The [21st.dev ReUI Data Grid Table](https://21st.dev/community/components/reui/data-grid-table/pinnable-columns-table) is a community read/sort/pagination table preview, not an Excel-like editor.

The primary job benchmark is the live [Handsontable Finance Dashboard](https://handsontable.com/demo#finance), which has grouped column headers, realistic financial data, cell edits, formula-driven calculations, currency formatting, and conditional gains/losses. Its adjacent live [Performance at Scale demo](https://handsontable.com/demo) exposes dataset sizes through 1M rows and virtual scrolling. Official [Handsontable keyboard shortcuts](https://handsontable.com/docs/react-data-grid/keyboard-shortcuts/) and [cell editor lifecycle](https://handsontable.com/docs/14.5/react-data-grid/cell-editor/) guidance were reviewed. [AG Grid keyboard interaction](https://www.ag-grid.com/javascript-data-grid/keyboard-navigation/) and [editing validation](https://www.ag-grid.com/react-data-grid/cell-editing-validation/) are supplemental evidence for keyboard boundaries, typed editor validation, invalid edit behavior and announcements. External products illustrate capabilities; no dependency or visual-theme adoption is proposed.

## Findings

- **The component name, story, and capability diverge:** the alias `DataGrid` suggests a general-purpose data grid, while current behavior is a small spreadsheet-style client editor with no sorting/filtering, columns schema, row identity, virtualization, copy/paste, fill, selection ranges, or formula evaluation. The public name/API scope needs an owner decision before consumer adoption.
- **The formula bar is not a formula engine:** its `fx` marker and “Formula Bar Input” label look like spreadsheet calculation, but the code stores and echoes plain strings and `onChange` emits the edited matrix. The value is not parsed/evaluated or recalculated. Do not describe this as live formulas or a ledger calculation surface.
- **Draft and server state boundary:** `initialData` initializes internal React state once; this is not a controlled `value` contract and later incoming data changes are not adopted. On commit the displayed local matrix changes immediately, and `onChange` returns the new matrix with no pending/success/rejection/conflict response contract or rollback path. This is not a durable ERP mutation interface. An application/service must own permission, tenant scope, data validation, atomic audit, conflict handling and confirmed results; if the component remains, specify how a rejected or stale edit is reconciled.
- **Editing lifecycle is incomplete:** source provides double-click/Enter editing, Enter/Tab commits, Escape cancels, and blur commits. No explicit `onEditCommit`/`onEditCancel` or per-cell validation exists. There is no printable-key entry, F2, page navigation, range selection, paste/fill, or grid-level error announcement. In the live browser, arrow navigation and Enter edit worked, Escape cancelled, but focus landed on the web area rather than the grid. More keys, focus return, `onBlur` behavior, and real assistive technology remain unverified.
- **Keyboard and semantics:** a semantic HTML table is given `role="grid"`, with table/row/cell/header roles, one focusable table and `aria-selected` on a cell. The AX tree shows associated visible column labels and cell values, but the formula coordinate and editor do not identify a domain field/value type. No screen reader tested whether the mixed native-table/grid pattern announces headers, row/column coordinates, selected cell, edit state and errors correctly. Scroll-region naming/focus and keyboard-only horizontal/vertical discovery are unverified.
- **Accessibility requirement contradiction:** column headers, row headers, ultra-compact cell text and formula bar use `var(--text-2xs, 10px)` or a 10px fallback. `DS-NFR-006` and ADR-0008 require supported text to remain at least 11 CSS px. The formula bar and input are explicitly 24px high for ultra-compact density; comfortable touch size and all rendered token results were not verified. The authored fallback itself conflicts with the minimum.
- **Data correctness and localization:** all Storybook financial amounts are strings (some with commas, signs, decimals, account codes, and totals), so edit commits change a cell to a string regardless of the original numeric type. No decimal/currency/unit model, locale formatting, formula dependency, row/column count validation, empty/unequal row behavior, duplicate/long header handling or data error path is specified. Displaying a financial-looking matrix does not authorize financial calculation or record mutation.
- **Responsive/density/performance:** the local root uses `inline-size` and `block-size: 100%`, a scrollable table container, sticky row/column headers and four cell-height variants; the story visually confirms a clear dense grid. Narrow screen/200% zoom, pinned-header behavior in both scroll axes, large-data limits, high contrast, RTL, other themes and computed density were not measured. The component materializes all rows/cells in the DOM and has no documented maximum; do not infer AG Grid/Handsontable scale behavior.
- **Business Suite consumer:** a repository search for `DataGrid` and `SpreadsheetGrid` found no direct Business Suite JSX/import. Storybook contains finance-budget/GL examples, which do not establish a production user problem or adopting route. The earlier search found no consumer; exact owner, real use case, contracts, and build/runtime integration remain unproven.
- **Evidence limits:** the live Handsontable finance grid visibly demonstrates a larger finance sheet with grouped headers, numeric formatting, calculated values, and conditional values. The local DataGrid render was the 6×7 budget example. The official shadcn table preview was 5 record rows and controls for selection/sorting/filtering; the community ReUI preview was a record table with sort affordances. These tasks are purposefully kept distinct. Screenshots were inspected in-session but not retained; there was no matched content theme/density/consumer route matrix.

## Required follow-up before elevation

1. Establish a PLT-ERP business use case and accountable workflow/data owner, or decide whether this unused export should remain, be renamed, or be deprecated. Repository absence is not itself permission to remove the current-major public export.
2. Contract the actual abstraction: general virtualized/read grid, safe local spreadsheet editor, or durable business record editor. Do not let the `DataGrid` alias imply sorting/query/server authority the component does not have.
3. Resolve the 10px typography fallback and touch-target requirement against ADR-0008 and DS-NFR-006; verify real computed tokens in all supported themes/densities.
4. If real edits are required, define typed columns/cells, decimal/currency/unit semantics as appropriate, validation, cancellation/commit, pending/success/rejection/conflict/reconciliation behavior, stable identity, and owner-controlled durable mutation contract before coding. If real formulas are not planned, rename or remove the formula affordance from the owned contract.
5. Prove keyboard and accessibility semantics at cell and editor transitions, including headers/coordinates, announcements, focus return, scroll reachability, high contrast, RTL and screen reader. Inspect copy/paste and larger dataset behavior only if the accepted task requires them.
6. Compare matching small/narrow and desktop views, all four densities and three Strata themes against the relevant spreadsheet benchmark; record screenshots bound to a source revision.
7. Verify an actual Business Suite workflow and package subpath integration after the calibration gate permits implementation. Maintain separation from `DataTable` and its calibration status.

## Readiness

**Overall: NOT VERIFIED.** The local table renders and a basic keyboard edit/cancel path was observed, but it is not yet shown to be a required Business Suite capability. The `DataGrid` name overstates its record-grid features; the formula-bar label overstates calculation; local edit state has no persistence/rollback boundary; the 10px fallback conflicts with an accepted requirement; and no consumer route was found. This is evidence-only; no implementation, tests, package changes, or consumer integration are claimed.
