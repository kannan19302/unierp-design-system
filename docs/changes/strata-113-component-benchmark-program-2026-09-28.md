# Strata 113-component reference benchmark program — 2026-09-28

Status: `PARTIAL`. Risk: `R2 — shared UI and Storybook evidence`. Accountable owner: PLT-DS; Business Suite journey owner: PLT-ERP. Scope is the current `@kannan19302/ui` package inventory and its Storybook evidence. No API, data, identity, permissions, contracts, package version, consumer lockfile, publication, deployment, release, or source-control change is authorized.

## Goal and acceptance criteria

Create a truthful, repeatable side-by-side review for every current package component, using the closest real online reference and the component's current Storybook stories. “Match” means align the task flow, composition, semantics, responsive behavior, states, and interaction patterns where appropriate, while retaining the UniERP/Strata token, accessibility, tenancy, and product requirements. Reference code, names, visual identity, or styles are not copied wholesale.

1. **AC-01 — Inventory denominator:** one ledger row for each component in the current generated package inventory; each row links its source and all component Storybook story IDs. A generated component count or five-file anatomy check is inventory evidence only, not readiness.
2. **AC-02 — Reference provenance:** each row records one task-fit primary online implementation reference and up to two supplemental references when they add a distinct interaction or accessibility pattern. Record exact URL, source/site, reference type, accessed date, and the behavior observed. General galleries or documentation that does not show the relevant pattern do not count as a reviewed implementation.
3. **AC-03 — Side-by-side evidence:** for each row, inspect the actual online implementation and current local Storybook story at comparable content, viewport, and interaction states. Record reference and Storybook evidence links or screenshot paths, observed differences, concrete changes needed, and the review date. Missing, inaccessible, non-equivalent, or unrenderable evidence stays `NOT VERIFIED` with a reason.
4. **AC-04 — Full Strata quality matrix:** determine task fit and semantic structure, interaction/keyboard behavior, loading/empty/error/disabled/selected/conflict states as applicable, responsive/reflow behavior, all three themes, all four densities where the component consumes density, LTR/RTL, accessibility/WCAG 2.2 AA, and representative Business Suite consumer use. Each axis is `PASS`, `GAP`, `NOT APPLICABLE` with rationale, or `NOT VERIFIED`; overall status cannot be `PASS` while any applicable axis is open.
5. **AC-05 — Evidence-based change packets:** group fixes by owner and dependency boundary. Follow the accepted Strata elevation protocol: broad catalog elevation remains withheld until the Input, DataTable, and Breadcrumb calibration packets each achieve `PASS`. This condition gates bulk code changes only; inventory preparation, source reading, references, and comparison research may continue. No broad green claim is inferred from the gate.
6. **AC-06 — Business Suite readiness:** independently prove provider package gates, current published consumer API compatibility, representative Business Suite journeys, and applicable accessibility/reflow/RTL/locale/financial semantics. Storybook-only evidence cannot satisfy consumer integration.
7. **AC-07 — Completion audit:** reconcile every current inventory row and applicable axis, run the required provider and consumer checks on supported runtimes, update owning PLT-DS/PLT-ERP traceability, and report designed, implemented, tested, integrated, deployed, and released separately. Completion requires all required design-system and consumer journey criteria to pass; deployment and release are reported only if separately authorized and evidenced.

## Reference selection and comparison method

Search the task and component behavior before choosing a reference. Prefer maintained, accessible, directly inspectable implementations with documented semantics and interaction states. Use the best equivalent available from shadcn/ui or another public UI implementation; retain source attribution and do not present a conceptually related page as a visual comparison. For application-specific ERP behaviors without a public direct equivalent, identify the closest pattern and record the limitation rather than claiming an exact match.

Capture matched viewport and state pairs. Compare information hierarchy, sizing, spacing, typography, control affordance, component anatomy, interaction transitions, keyboard and screen-reader behavior, narrow-screen composition, and token/theme behavior. Describe differences as observations and make changes only where they improve the UniERP task and satisfy the product standards. A visually close screenshot does not prove accessible interaction or functional correctness.

Store compact references, notes, state, and evidence paths in `docs/evidence/strata-component-benchmarks.csv`; keep screenshots and generated run reports in the existing evidence/test-results locations and link them. Do not record credentials, private tenant data, or personal data. Review every row against the actual current source and browser output; generated references are only an index. No row may be set to `PASS` by inference from file existence, exported symbol count, story count, unit tests, aggregate scores, or a different component's benchmark.
