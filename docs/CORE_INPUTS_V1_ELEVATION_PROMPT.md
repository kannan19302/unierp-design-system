---

Upgrade the components under `D:\UniERP\design-system\src\core\inputs` to the approved Strata V1 quality demonstrated by `Core/Navigation/Sidenav` in Storybook. Keep the official release designation at V1. Use SideNav V1 as a benchmark for visual restraint, interaction completeness, accessibility, Storybook clarity and reviewability. Design each input for its own task; do not add sidebar controls or customization features where they do not belong.

Follow `D:\UniERP\AGENTS.md`, `D:\UniERP\design-system\AGENTS.md`, the enterprise-brain skill and the owning design-platform requirements before material work. Preserve all existing uncommitted changes. Use the Strata visual foundations as the source of truth: Nova direction, neutral base and theme, Inter typography, Lucide icons, solid surfaces, subtle menu accents and the approved token radius scale. Use semantic tokens and CSS logical properties. Do not copy shadcn code or introduce a second visual system.

First, discover the current inputs from source and the generated component inventory. For every registered input, report its public API, owner/consumers, existing stories, behavior and a11y tests, visual/state gaps, duplicates or obsolete stories, and dependency on lower-level controls. Define numbered acceptance criteria and a dependency-ordered plan. Classify the knowledge delta and identify the exact authoritative files and evidence that need updating. Do not treat a file count or passing build as proof of quality.

Build a coherent input-family foundation before polishing individual controls: field height by density, labels, help text, placeholders, borders, focus rings, validation feedback, prefix/suffix icons, menus, popovers and disabled/readonly treatment. Keep a quiet, clean enterprise appearance consistent across light, dark and high-contrast themes. Respect RTL, 200% zoom, supported small screens and reduced motion. Avoid one-off raw values and cosmetic effects that reduce legibility.

Implement the first representative pilot in Storybook, preferably a complex input such as Combobox, and present it for visual review. The pilot must demonstrate a real controlled interaction, keyboard operation, focus and error handling, density and theme behavior, responsive layout, and a current V1 state matrix. Use synthetic examples. Incorporate review feedback into the family recipe before applying it to the remaining inputs. Then proceed component by component in dependency order, keeping each slice buildable and reviewable.

For each input, preserve compatible public behavior and its five-file anatomy. Cover applicable default, hover, focus, filled, disabled, readonly, required, invalid, loading, empty and success states. Test native semantics, label/help/error association, keyboard and assistive-technology behavior, pointer/touch operation and the input-specific edge cases: IME/composition and paste for text, decimal/currency precision for numbers, locale/time-zone boundaries for dates, selection/focus for composite lists, and size/type/retry behavior for uploads. Do not invent states or features that have no purpose for that control.

Keep Autodocs and a meaningful `StateMatrix` or `AllStatesGallery`. Replace superseded legacy Storybook stories only after checking story-ID references; remove duplicate or stale entries rather than accumulating V1 and old versions. Provide a clear interactive primary V1 story for each component. Do not change downstream application repositories until the design-system package and Storybook pass their gates, then validate any affected consumers.

Run the affected repository's token, logical-property, density, contrast, inventory, governance, typecheck, lint, focused Vitest/axe, full test, package build and Storybook checks. Inspect relevant stories in the browser for keyboard behavior, visual consistency and accessibility findings across the risk-based theme/density/RTL/responsive matrix. Report exact commands, pass/fail/incomplete results and remaining risks. Review the complete diff before handoff. Do not commit or push without the exact human authorization required by the canonical protocol.

At every handoff, provide an inventory/progress table per input, Storybook review links, acceptance-criterion states, a knowledge-delta report and the required UniERP Iteration Evidence Report. Claim `VERIFIED COMPLETE` only when every in-scope input and validation gate is satisfied; otherwise use the protocol's truthful partial, pending, blocked or failed status.
